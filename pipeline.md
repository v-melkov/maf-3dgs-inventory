# Сквозной пайплайн обработки: этапы 00–07

Спецификация первой части технологического процесса — от исходного видеофайла
до обученной 3DGS-модели объекта в формате `.ply`.

Материал для п. 3.1.1–3.1.7 ВКР.

---

## 0. Принципы построения

**Сессия — единица обработки.** Все объекты одного съёмочного полигона
обрабатываются в рамках одной сессии: оценка поз камер (COLMAP) выполняется
однократно по всем кадрам, поэтому все объекты сессии оказываются в единой
системе координат, а масштабный коэффициент, определённый по эталону,
применим ко всем моделям сессии. Это прямо следует из п. 2.4.6.5 методики
и является причиной, по которой объект не может быть единицей обработки.

**Этап — отдельный вызов.** Каждый этап читает артефакты предыдущих этапов,
пишет только в собственный каталог и оставляет отчёт. Повторный запуск при
наличии готового результата пропускается; `--force` перезапускает этап.
Удаление каталога этапа эквивалентно его сбросу.

**Отказ с диагнозом.** Этап не продолжает работу при невыполнении
предусловий. Сообщение об отказе содержит: что проверялось, что получено,
что ожидалось, какое действие требуется от оператора.

**Три вида контроля.**

| Вид | Обозначение | Поведение |
|---|---|---|
| Автоматическая проверка | А | Числовой критерий, отказ или предупреждение без участия оператора |
| Визуальный контроль | В | Формируется изображение в `qc/`; обязательный — требует подтверждения оператора, рекомендуемый — только сохраняется |
| Интерактивный ввод | И | Обработка приостанавливается до выбора оператора; выбор сохраняется и при повторном запуске не запрашивается |

## 2. Контракт этапа

Каждый модуль этапа реализует:

```
check_preconditions(session) -> list[Problem]   # до любых вычислений
run(session, config, force) -> StageReport
write_qc(session) -> list[Path]
```

`StageReport` сериализуется в `<NN>_*_report.json` и включает:

```json
{
  "stage": "05_sfm",
  "status": "ok | ok_with_warnings | failed",
  "started": "2026-08-12T10:31:05+03:00",
  "duration_s": 1847.2,
  "tool_versions": {"colmap": "3.11.1", "python": "3.11.9"},
  "params": { },
  "metrics": { },
  "warnings": [ ],
  "qc_images": [ ],
  "inputs_sha256": { }
}
```

`inputs_sha256` фиксирует состояние входных артефактов. Если хеш входа
изменился, а этап помечен выполненным, при следующем запуске выдаётся
предупреждение о рассогласовании — это защищает от ситуации, когда кадры
переизвлекли, а COLMAP остался от предыдущего прогона.

`session.json` агрегирует статусы всех этапов и служит источником сведений
для инвентарной карточки (`n_frames`, `geo_rmse`, `scale_factor` и др.).

## 3. Этап 00 — приём исходного материала

**Назначение.** Инвентаризация входа, фиксация контрольных сумм, извлечение
технических характеристик записи.

**Действия.** `ffprobe -show_format -show_streams -print_format json` по
каждому файлу; SHA-256; сортировка файлов по времени создания.

**Проверки (А).**

| Проверка | Критерий | Действие при нарушении |
|---|---|---|
| Файлы найдены | ≥ 1 файл видео | Отказ |
| Длительность | ≥ 30 с | Отказ |
| Разрешение | ≥ 3840 по длинной стороне | Предупреждение (п. 2.4.2) |
| Частота кадров | ≥ 30 fps | Предупреждение |
| Наличие потока данных | поток с `codec_type=data` | Предупреждение: трек ГНСС может отсутствовать |
| Непрерывность серии | разрыв между файлами < 2 с | Предупреждение с указанием величины разрыва |

**Нештатные ситуации.**

*Запись разбита на несколько файлов.* Камера режет запись по достижении
предельного размера файла. Файлы обрабатываются как единая последовательность;
временное смещение второго и последующих файлов вычисляется как сумма
длительностей предыдущих. Порядок определяется по `creation_time`, а не по
имени файла, — имена могут не совпадать с порядком при перезаписи карты.

*Переменная частота кадров.* Если `avg_frame_rate ≠ r_frame_rate`, привязка
номера блока ко времени становится нелинейной. Отказ с рекомендацией
предварительно перекодировать запись с постоянной частотой.

## 4. Этап 01 — приведение к перспективной проекции

Этап выполняется только для источников с неперспективной проекцией
(эквиректангулярная развёртка, «рыбий глаз»). Для обычной камеры
пропускается, и `02_frames` формируется непосредственно из `00_raw`.

**Действия.** Для каждого из N виртуальных направлений формируется отдельный
видеопоток фильтром `v360` библиотеки ffmpeg с заданными азимутом, углом
места, горизонтальным полем зрения и выходным разрешением.

**Проектные решения, требующие фиксации в тексте ВКР.**

- Число направлений N и их азимуты определяют угловое перекрытие между
  смежными виртуальными видами. При поле зрения H° перекрытие составляет
  `N·H/360 − 1`. Для COLMAP требуется перекрытие не менее 70–80 % (п. 2.4.5),
  но это требование относится к смежным во **времени** кадрам, а не к
  смежным виртуальным направлениям одного момента.
- Виртуальные виды одного момента имеют общий центр проекции. Для SfM это
  вырожденная конфигурация: они не дают базиса и не участвуют в
  триангуляции между собой. Полезны они тем, что расширяют угловое покрытие
  сцены и увеличивают число наблюдений каждой точки.
- Все виртуальные камеры имеют идентичные внутренние параметры и нулевую
  дисторсию, что позволяет на этапе 05 использовать модель `PINHOLE` с общими
  параметрами (`--ImageReader.single_camera 1`) и не применять режим `--gut`
  в LichtFeld Studio. Это существенное упрощение по сравнению с обработкой
  кадров реальной широкоугольной камеры.

**Проверки.**

- (А) Соотношение сторон исходного видео 2:1 — признак эквиректангулярной
  развёртки. При ином соотношении — отказ с указанием, что источник, вероятно,
  уже перспективный.
- (А) Оценка потребного дискового объёма до запуска; отказ при нехватке
  места с указанием требуемой и доступной величины.
- (В, рекомендуемый) Первый кадр каждого виртуального потока в `qc/` —
  контроль отсутствия геометрических искажений и правильности азимутов.

**Нештатные ситуации.** Аварийное завершение ffmpeg на одном из потоков:
удалить частично записанный файл, повторить только этот поток, при повторном
отказе — отказ этапа с последними строками вывода ffmpeg в отчёте.

## 5. Этап 02 — извлечение кадров и присвоение временных меток

Наиболее ответственный этап с точки зрения последующей геопривязки.

### 5.1. Особенность инструмента

Sharp Frame Extractor версии 2 разбивает запись на последовательные блоки и
сохраняет самый резкий кадр каждого блока под именем `frame-NNNNN.png`, где
NNNNN — **номер блока, а не номер кадра в исходном видео**. Сведения о том,
какому моменту времени соответствует сохранённый кадр, инструмент не
возвращает.

Отсюда два следствия, определяющих конструкцию этапа.

**Режим `--every` вместо `--count`.** При задании числа кадров (`--count N`)
фактическое их количество приблизительное и границы блоков заранее
неизвестны. Поэтому требуемое число кадров пересчитывается в интервал
`S = T / N` (T — длительность записи), и вызов выполняется в форме
`--every S`. Границы блоков становятся детерминированными: блок k покрывает
интервал `[k·S, (k+1)·S)`.

**Время кадра назначается серединой блока.** Точное положение выбранного
кадра внутри блока неизвестно, поэтому принимается
`t_k = t_0 + (k + 0,5)·S`. Возникающая погрешность равномерно распределена
на интервале ±S/2 и при скорости движения оператора v даёт смещение
положения до `v·S/2`. При S = 0,3 с и v = 1 м/с это 0,15 м — величина,
на порядок меньшая собственной погрешности автономного определения координат
(п. 2.4.4.2), но её следует зафиксировать в бюджете погрешностей как
самостоятельную составляющую.

### 5.2. Начало отсчёта времени

`t_0` — момент начала записи в шкале ГНСС. Возможны два источника:

1. **Трек извлекается из того же видеофайла** (конфигурация настоящего
   эксперимента). Тогда первая точка трека соответствует началу записи, и
   `t_0` берётся из неё. Шкалы времени камеры и приёмника совпадают по
   построению, процедура согласования шкал (п. 2.4.4.3) не требуется, а
   систематическая составляющая погрешности синхронизации равна нулю.
   Это существенное преимущество конфигурации, которое следует отметить
   в тексте.
2. **Внешний регистратор трека.** `t_0` определяется по метаданным видеофайла
   (`format_tags.creation_time`), к нему применяется поправка, полученная
   съёмкой индикатора точного времени. Общий случай, описанный в методике.

### 5.3. Преобразование формата

Утилита `gpscorrelate` работает **только с файлами JPEG**. Экстрактор выдаёт
PNG. Следовательно, между этапами 02 и 04 обязательно преобразование формата
с одновременной записью временных меток в EXIF.

Записываются:

| Тег | Значение |
|---|---|
| `DateTimeOriginal` | `t_k` в UTC, посекундно |
| `SubSecTimeOriginal` | дробная часть `t_k` (gpscorrelate использует её для уточнения интерполяции) |
| `OffsetTimeOriginal` | `+00:00` — явно, чтобы исключить неоднозначность часового пояса |
| `ImageDescription` | `<session_id>/<virtual_cam>/<block>` — для прослеживаемости |

Качество JPEG принимается 97 при отключённом субдискретизировании цветности
(4:4:4). Обоснование допустимости: исходный материал — видеозапись с
межкадровым сжатием, вносимая дополнительно погрешность квантования
пренебрежима по сравнению с уже присутствующей. Значение параметра
фиксируется в отчёте этапа.

### 5.4. Собственная оценка резкости

Экстрактор не возвращает значения показателя резкости выбранных кадров.
Показатель Тененграда вычисляется повторно для сохранённых кадров и
записывается в `frames.json`. Это даёт:

- распределение резкости по выборке — материал для протокола качества;
- возможность отбраковки кадров, оказавшихся резкими лишь относительно
  своего блока (весь блок смазан);
- количественное обоснование выбора интервала S.

### 5.5. Проверки

| Вид | Проверка | Действие |
|---|---|---|
| А | Число полученных файлов ≥ 0,9·N | Предупреждение с указанием фактического числа |
| А | Ни один кадр не имеет резкости ниже 0,3 медианы | Отбраковка с занесением в протокол |
| А | Все имена уникальны в пределах сессии | Отказ (коллизия имён между виртуальными потоками) |
| В (рекомендуемый) | Контактный лист: 24 кадра, равномерно по выборке | Оценка равномерности покрытия и отсутствия смаза |

**Нештатные ситуации.** Экстрактор не создал ни одного файла — проверить,
что видеофайл декодируется (`ffmpeg -v error -i file -f null -`), и выдать
вывод декодера в отчёт. Нехватка оперативной памяти — понизить `--workers`
и повторить; при повторном отказе указать оператору параметр `--memory-limit`.

## 6. Этап 03 — извлечение и подготовка трека

**Действия.** `pyosmogps --timezone-offset <TZ> --frequency <f>
--resampling-method <m> extract <входные файлы> track.gpx`.

Сырой трек сохраняется отдельно (`track_raw.gpx`, без ресемплинга) как
первичный материал; для дальнейшей обработки используется
ресемплированный.

**Выбор частоты и метода.** Методика (п. 2.4.4.1) требует не реже одной
отметки в секунду. Низкочастотная фильтрация (`lpf`) сглаживает шум, но
вносит запаздывание и искажает траекторию на резких поворотах — а обход
объекта по кругу состоит преимущественно из поворотов. Для настоящей задачи
предпочтительна линейная интерполяция (`linear`) при частоте 2–5 Гц.
Целесообразно сформировать оба варианта и включить сопоставление невязок
геопривязки по ним в результаты эксперимента: это дешёвая дополнительная
таблица.

**Проверки.**

| Вид | Проверка | Действие |
|---|---|---|
| А | Число точек > 0 | Отказ: трек не записан (пульт не был подключён либо не было решения ГНСС) |
| А | Интервал трека покрывает интервал записи | Отказ с указанием обоих интервалов |
| А | Максимальный разрыв между точками | > 5 с — предупреждение, участок отмечается как ненадёжный |
| А | Скачки положения | Смещение между смежными точками > 3·медианы — отметка потенциально грубой ошибки |
| А | Протяжённость трека | Сопоставление с ожидаемым размером полигона; расхождение на порядок — предупреждение |
| В (обязательный) | Трек в плане и профиль высоты | Оператор подтверждает, что траектория соответствует выполненному обходу |

**Нештатные ситуации.**

*Инструмент не распознаёт модель камеры.* Утилита проверяет совместимость
входного файла и заявляет поддержку моделей Osmo Action 4, 5 и 6. Для иных
моделей серии совместимость не гарантирована. При отказе распознавания —
отказ этапа с рекомендацией перейти на альтернативный источник трека
(внешний регистратор, п. 2.4.4.1, вариант 3), что не изменяет структуры
методики.

*Неоднозначность часового пояса.* Смысл параметра `--timezone-offset`
документирован неполно (в документации инструмента встречаются оба написания —
`--timezone-offset` и `--time-offset`). Требуется однократная проверка:
сопоставить время первой точки трека с временем начала записи по метаданным
файла. Расхождение, кратное целому числу часов, — признак неверного
параметра. Результат проверки фиксируется в конфигурации сессии.

## 7. Этап 04 — присвоение координат кадрам

**Действия.**

```
gpscorrelate -g 03_track/track.gpx \
             -z 0 --no-photo-tz \
             -m <max_dist> -M -v -R \
             02_frames/images/*.jpg
```

`-z 0` в сочетании с записью `DateTimeOriginal` в UTC (п. 5.3) исключает
любые преобразования часовых поясов. `-m` ограничивает интерполяцию через
разрывы трека. `-M` сохраняет время модификации файлов, что важно для
контроля целостности по хешам.

**Коды возврата.** 0 — успех; 1 — грубая ошибка (чтение/запись); 2 — трек
не покрывает время части изображений. Код 2 обрабатывается не как отказ,
а как основание для анализа: если координаты не получила малая доля кадров
на краях записи — предупреждение; если значительная доля или кадры в
середине — признак рассогласования шкал времени, отказ.

**Проверки.**

| Вид | Проверка | Действие |
|---|---|---|
| А | Доля кадров с координатами | < 95 % — предупреждение; < 80 % — отказ |
| А | Разброс координат по выборке | Сопоставляется с размером полигона: нулевой разброс означает, что всем кадрам присвоена одна точка; разброс в километрах — ошибка сопоставления |
| А | Монотонность | Координаты, упорядоченные по времени, не должны содержать возвратов, превышающих точность приёмника |
| В (рекомендуемый) | Точки съёмки поверх трека | Наглядно показывает, легли ли кадры на траекторию |

Контроль выполняется машиночитаемым выводом `gpscorrelate --show --machine`
по всем файлам — это даёт таблицу «файл, время, широта, долгота, высота»,
пригодную и для протокола, и для последующей геопривязки без повторного
чтения EXIF.

## 8. Этап 05 — оценка поз камер

**Действия.** Последовательность вызовов COLMAP:

1. `feature_extractor` — `--ImageReader.camera_model PINHOLE`,
   `--ImageReader.single_camera 1` (обосновано в п. 4).
2. Сопоставление: `exhaustive_matcher` при числе кадров до ~400,
   `sequential_matcher` с обнаружением петель — при большем.
   Для набора из нескольких виртуальных потоков последовательное
   сопоставление некорректно: соседние по имени кадры принадлежат разным
   направлениям. Либо применяется исчерпывающее сопоставление, либо порядок
   имён выстраивается по времени, а не по потоку.
3. `mapper` → `sparse/`.
4. `model_analyzer` — источник числовых показателей качества.

**Кадры не маскируются** (п. 2.4.6.5): фон необходим для восстановления
геометрии съёмки, а эталон должен быть виден.

**Проверки.**

| Вид | Проверка | Критерий | Действие |
|---|---|---|---|
| А | Число построенных подмоделей | 1 | > 1 — **критическая ситуация**, см. ниже |
| А | Доля зарегистрированных изображений | ≥ 90 % | 70–90 % — предупреждение; < 70 % — отказ |
| А | Средняя ошибка репроекции | ≤ 1,0 px | > 1,5 px — предупреждение |
| А | Средняя длина трека точки | ≥ 4 | Меньшее значение указывает на слабое перекрытие |
| А | Наличие эталона в кадрах | ≥ 10 кадров с маркерами ArUco | Отказ: масштабирование будет невозможно |
| В (обязательный) | Разрежённое облако и положения камер в плане | — | Оператор подтверждает связность траектории |
| В (обязательный) | Наложение позиций камер SfM на трек ГНСС после грубого совмещения | — | Расхождение формы траекторий — признак развала реконструкции |

**Развал реконструкции на несколько подмоделей** — наиболее частая и наиболее
дорогая по последствиям нештатная ситуация: обработка формально завершается
успешно, но модели соответствуют разным участкам сцены и объединить их
нельзя. Автоматическое действие: выбрать подмодель с наибольшим числом
изображений, вывести распределение изображений по подмоделям и **потребовать
явного подтверждения оператора** перед продолжением. Типичные причины —
недостаточное перекрытие при быстром движении, участок с однородным фоном,
слишком большой интервал S на этапе 02.

**Прочие нештатные ситуации.** Нехватка видеопамяти при сопоставлении —
понизить `--SiftMatching.max_num_matches`. Отсутствие CUDA — переход на
`--SiftExtraction.use_gpu 0` с предупреждением о кратном росте времени.

## 9. Этап 06 — сегментация объектов

Единственный этап, требующий обязательного участия оператора.

### 9.1. Проблема выбора объекта

Текстовый запрос детектора с открытым словарём возвращает все объекты,
соответствующие описанию. В типичной сцене благоустройства объекты учёта
расположены близко: в одном кадре могут одновременно присутствовать скамейка,
урна и контейнерная площадка. Автоматический выбор по наибольшему
доверительному значению или по наибольшей площади ненадёжен и не
воспроизводим.

### 9.2. Порядок

1. Оператор задаёт идентификатор объекта и текстовый запрос:
   `stage06 --object bench-01 --prompt "wooden bench"`.
2. Детектор обрабатывает подмножество кадров (каждый k-й), выбирается
   **опорный кадр** — тот, на котором объект наблюдается наиболее полно
   (максимальная площадь рамки при доверительном значении выше порога и
   без касания границ кадра).
3. **(И)** Если на опорном кадре обнаружено более одной рамки, формируется
   изображение с пронумерованными рамками, и оператор указывает номер.
   При единственной рамке подтверждение не запрашивается.
4. Выбранная рамка передаётся модели сегментации как промпт на опорном кадре.
5. Маска распространяется по последовательности в прямом и обратном
   направлениях относительно опорного кадра.
6. Результат сохраняется в `masks/` с именами, соответствующими именам кадров.
7. Выбор оператора (опорный кадр, координаты рамки, промпт, доверительное
   значение) сохраняется в `object.json` и при повторном запуске
   используется без запроса — это обеспечивает воспроизводимость.

**При нескольких виртуальных потоках** процедура выполняется для каждого
потока отдельно: механизм потоковой памяти работает на непрерывной
последовательности, а кадры разных направлений такой последовательности не
образуют. Объект может быть не виден в части потоков — это штатная ситуация,
поток исключается из обработки данного объекта с отметкой в протоколе.

### 9.3. Проверки (реализация п. 2.4.6.4)

| Вид | Проверка | Действие |
|---|---|---|
| А | Наличие маски на каждом кадре | Кадры без маски исключаются из обучающей выборки |
| А | Устойчивость площади | Относительное изменение площади между смежными кадрами > порога — кадр отмечается |
| А | Связность | Изолированные фрагменты далее заданного расстояния от основной области — признак захвата постороннего объекта |
| А | Касание границ кадра | Кадр сохраняется, но учитывается отдельно |
| А | Доля отбракованных кадров | > 20 % — отказ: сегментация неустойчива, требуется другой опорный кадр или уточнение запроса |
| В (обязательный) | Наложение маски на 12 кадров, равномерно по последовательности | Оператор подтверждает, что выделен один и тот же объект на всём протяжении |
| В (обязательный) | График площади маски по номеру кадра | Ступенчатые изменения — признак «перескока» маски на соседний объект |

Доля отбракованных кадров фиксируется как показатель качества этапа и входит
в состав сведений об обследовании (п. 2.6.2).

### 9.4. Эталон как объект

Линейный эталон обрабатывается как обычный объект учёта (`ruler-01`) —
это реализация контрольного прогона, предусмотренного п. 3.2.4. Его габариты
известны независимо, что даёт системную составляющую погрешности метода,
отделённую от особенностей формы конкретного МАФ.

## 10. Этап 07 — обучение 3DGS-модели

**Действия.**

```
lichtfeld-studio -d <подготовленный каталог> -o 07_models/<object_id> \
                 --headless --train \
                 --mask-mode segment \
                 --output-name splat \
                 --iter <N> --strategy mcmc \
                 --eval --save-eval-images \
                 --log-file train.log --log-level info
```

Режим `--mask-mode segment` соответствует задаче: гауссианы формируются
только для области объекта. Режимы `ignore` и `alpha_consistent` решают
другие задачи и в настоящей методике не применяются. Отсутствие
`--gut` обосновано в п. 4 (модель камеры — `PINHOLE`).

**Подготовка входного каталога.** Обучение требует каталога в структуре
COLMAP: разрежённая модель из `05_sfm/sparse/0`, изображения и маски.
Расположение каталога масок, ожидаемое средой обучения, требует уточнения
по исходному коду версии — параметр `--images` задаёт имя каталога
изображений, аналогичный параметр для масок в справке не документирован.
До уточнения каталог формируется симлинками, что позволяет изменить схему
без переизвлечения кадров.

**Проверки.**

| Вид | Проверка | Действие |
|---|---|---|
| А | Доступность CUDA и объём видеопамяти | Отказ до запуска с указанием требуемого объёма |
| А | Число кадров с масками ≥ 40 | Меньшее — предупреждение о заведомо низком качестве |
| А | Выходной `.ply` создан и непуст | Отказ |
| А | Число гауссианов в модели | Аномально малое (< 10⁴) — признак того, что маски инвертированы |
| А | Показатели `--eval` | Фиксируются в отчёте как характеристика качества реконструкции |
| В (обязательный) | Просмотр модели в интерфейсе среды | Оценка визуального качества и отсутствия грубых артефактов |

**Нештатные ситуации.**

*Нехватка видеопамяти.* Последовательное понижение: `--tile-mode 2` → `4`,
затем `--resize_factor 2`, затем `--max-cap`. Каждое понижение фиксируется
в отчёте, поскольку влияет на достижимую точность и должно учитываться при
сопоставлении результатов по объектам.

*Маски инвертированы.* Признак — обучение сходится к модели фона.
Обнаруживается по числу гауссианов и по изображениям `--save-eval-images`.
Исправление — флаг `--invert-masks`.

*Модель обучилась, но объект «полый».* Признак недостаточного углового
покрытия. Не является отказом этапа, но должно быть отмечено: на этапе
построения OBB это приведёт к занижению габарита.
